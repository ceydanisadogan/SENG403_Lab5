0 · The example

Code · grade.py 
 1  def grade(score):
 2      if score < 0 or score > 100:
 3          return "error"
 4      if score >= 50:
 5          result = "pass"
 6      else:
 7          result = "fail"
 8      return result
Tests · test_grade.py 
def test_pass():
    assert grade(70) == "pass"

def test_error():
    assert grade(-5) == "error"

This code has 7 statements: lines 1–5, 7 and 8. The line else: is not a statement, but the def line counts as one. The code has 2 decisions (lines 2 and 4), so it has 4 branches.

1 · Words

WordMeaning
StatementA statement is one instruction in the code. It is usually one line.
DecisionA decision is a place where the code chooses a way, for example if or while. It has two outcomes: true and false.
BranchA branch is one outcome of a decision. One if has 2 branches.
ConditionA condition is one small part of a decision. For example, score < 0 or score > 100 is one decision with two conditions.
CoverageCoverage = the items that our tests ran ÷ all items × 100 %.
MutantA mutant is a copy of the code with one small change.
KilledA mutant is killed when at least one test fails on it. This is good.
SurvivedA mutant survived when all tests pass on it. This means that the tests did not notice the change.
Mutation scoreMutation score = the mutants that were killed ÷ all mutants.

2 · Statement and branch coverage

Statement coverage

Statement coverage = the statements that the tests ran ÷ all statements.

Example: line 7 never ran, so the statement coverage is 6 of 7 = 86 %.

Branch coverage

Branch coverage = the branches that the tests took ÷ all branches. For 100 %, every decision must be true once and false once.

Example: line 4 was never false, so the branch coverage is 3 of 4 = 75 %.

Remember this rule: 100 % branch coverage always gives 100 % statement coverage. The opposite is not true.

How do you close a gap? First, find an input that goes to the missing line or branch. In this example, any score from 0 to 49 works. Then take the expected result from the specification. With one more test, grade(30) == "fail", both numbers become 100 %.

Be careful with a decision that has or or and. Branch coverage looks only at the final answer of the whole decision. With the inputs −5 and 70, line 2 was true once and false once. But the part score > 100 was never true. So nobody tested the upper limit.

3 · How to read the report

Python · coverage.py (pytest-cov) 
Name       Stmts   Miss Branch BrPart  Cover   Missing
grade.py       7      1      4      1    82%   7
2 passed
StmtsThis is the number of all statements.
MissThis is the number of statements that never ran.
BranchThis is the number of all branches.
BrPartThis is the number of decisions that ran but went only one way.
CoverThis number puts statements and branches together. See the formula on the right.
MissingThese are the line numbers that never ran. 4->7 means that the jump from line 4 to line 7 never happened.
The formulas 
statements run   = Stmts - Miss              = 7 - 1 = 6
statement cov.   = statements run / Stmts    = 6 / 7 = 86 %

Cover            = (statements run + branches taken)
                   / (Stmts + Branch)        = (6 + 3) / (7 + 4) = 82 %

branches taken   = Cover x (Stmts + Branch) - statements run
                 = 0.82 x 11 - 6 = 9 - 6     = 3   (round to a whole number)
branch cov.      = branches taken / Branch   = 3 / 4 = 75 %

A branch in a line that never ran is also missed. So the number of branches taken can be smaller than Branch − BrPart.

Java · JaCoCo (target/site/jacoco/index.html)
Green lineThe line ran.
Red lineThe line never ran.
Yellow line with a diamondThe decision went only one way. Put the mouse on the diamond to see a message like "1 of 2 branches missed".
Missed Branches"3 of 8" means that 3 branches were missed, so 5 of the 8 branches were taken.
Missed · LinesThe first number is the lines that never ran. The second number is all lines.
Two tools count in two ways

coverage.py counts a whole if a or b as 2 branches. JaCoCo counts each condition, so if (a || b) has 4 branches. JaCoCo counts only the lines of code inside methods. It does not count the method header or the constants. Because of this, the Python numbers and the Java numbers are not the same. Both of them are correct.

4 · What 100 % coverage does not prove

def test_grade():
    grade(70)
    grade(30)
    grade(-5)        # no assert!

This test gives 100 % statement coverage and 100 % branch coverage. But this test can never fail.

Coverage cannot see these things:

  • It cannot see whether a test checks the result.
  • It cannot see code that is missing. A forgotten rule has no line.
  • It cannot see a wrong value at a boundary.

Coverage shows you what you did not test. It does not show you what you tested well.

5 · Mutation testing: we test the tests

The tool makes one small change in the code. This changed copy is a mutant. Then the tool runs your tests on the mutant. Good tests must fail on it. Before this, all tests must pass on the original code.

Code and tests (100 % branch coverage) 
 1  def bill(qty, member):
 2      price = qty * 10
 3      if qty >= 5:
 4          price = price - 5
 5      if member:
 6          price = price - 2
 7      return price

assert bill(8, True) == 73
assert bill(1, False) == 10
The output of python mutation_run.py 
ID   Line  Change    Result    Mutated line
M01  2     * -> /    killed    price = qty / 10
M02  3     >= -> >   SURVIVED  if qty > 5:
M03  4     - -> +    killed    price = price + 5
M04  6     - -> +    killed    price = price + 2
Killed 3 of 4 mutants.
Mutation score = 3 / 4 = 75 %
Survivors: M02 (line 3)

How to kill a mutant that survived

  1. Read the change. Ask this question: for which input do the original code and the mutant give different results? For M02, only qty = 5 gives a different result.
  2. Look for a test with that input. If there is no such test, add one. If there is one, check that it checks the result with an assert. If it has no assert, add the assert.
  3. Take the expected value from the specification, not from the code. For example, the rule "5 TL off for 5 bottles or more" gives bill(5, False) == 45.
  4. Run the tests on the original code. Are they green? Then run the mutation tool again. Is a test red? Then the original code does not follow the specification. You found a defect.
Java · PIT (target/pit-reports/index.html)
KILLEDA test failed on the mutant.
SURVIVEDThe tests ran the line, and all of them passed.
NO_COVERAGENo test runs this line. Count it as "not killed".
changed conditional boundary> ↔ >=, < ↔ <=
negated conditional== ↔ !=, > → <= …
replaced integer subtraction with addition- → +
replaced int return with 0return x → return 0
Good to know

The console line >> Generated 20 mutations Killed 15 (75%) gives the mutation score: killed ÷ all.

When you change the code, the list of mutants can change too.

Some mutants behave exactly like the original code. They are called equivalent mutants. No test can kill them, so a person must decide about them.

7 · A defect report in five lines

Title:    Senior ticket price is wrong for age 65
Steps:    Call price(65)
Expected: 50  (specification: "Age 65-120: senior, 50 TL")
Actual:   80
Evidence: test_price[65-50] fails: "assert 80 == 50"

Here is how you test your report: can a classmate repeat the bug with only your five lines? Before you write the report, check that your expected value is correct. A wrong test is not a defect in the code.
